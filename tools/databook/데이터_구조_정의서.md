# POUR 협약사 데이터 구조 정의서 v1

작성 2026-11-20 · 첫 적용 자료 기준일 2026-10-20

## 1. 왜 이 구조인가

- 원본 자료가 여러 파일에 흩어져 있고, 같은 업체·같은 단지를 서로 다른 이름으로 적고 있음.
- 그래서 지표마다 정의가 달라지고, 사람마다 다른 숫자를 봄.
- 이 정의서는 **표준 표 5개**와 **열쇠 3개**를 정함.
- 보고서, KPI 화면, 데이터북은 모두 이 표준 표만 읽음.
- 원본이 바뀌어도(12/25 앱 전환 포함) 표준 표의 모양은 그대로 둠. 생성기만 고침.
- 요청 활동은 **플랫폼(앱) 내보내기와 잔디 PT 목록에서 생성기가 직접 만듦.** 예전처럼 따로 정리한 원장 파일이 없어도 됨(2026-11-20 전환).

## 2. 흐름

```
원본 파일들 ──(생성기 build_databook.py)──▶ 표준 표 5개(CSV) ──▶ ① 데이터북(시트)
                                                              ├▶ ② 고객관리카드 KPI 화면(“데이터 파일로 최신화”)
                                                              └▶ ③ 보고서(선행지표 등)
```

- 원본은 고치지 않음. 날짜 폴더에 그대로 보관함.
- 표준 표는 매번 원본에서 **새로 만듦**. 표준 표나 데이터북을 손으로 고치면 다음 갱신 때 사라짐.
- 고칠 것이 있으면 원본을 고치거나 규칙(config의 `cohort_rules` 등)에 적음.

## 3. 열쇠 3개

| 열쇠 | 모양 | 무엇을 잇나 | 지금 상태 | 앞으로 |
|---|---|---|---|---|
| 통합ID | `B2B201` | 업체 ↔ 요청·판매·PT·공고 | 업체명이 명부와 정확히 같거나 **별칭표(aliases)**에 있을 때 붙음 | 앱 등록·판매 기록에서 업체를 통합ID(또는 사업자번호)로 고르게 함 |
| 단지키 | 단지명을 유니코드 정규화(Ⅱ→II)하고 공백 빼고 소문자로 | 요청 ↔ PT ↔ 공고 | 이름 대조라 표기가 다르면 못 이음 | K-APT 단지코드를 요청에 함께 남김 |
| 공종키 | 공백 빼고 소문자, `+`·`,`로 나눠 가나다순으로 다시 이음 (`에폭시+균열보수및재도장` → `균열보수및재도장+에폭시`) | 같은 단지의 같은 공사인지 | 생성기 규칙 | 앱의 공종 선택값을 그대로 씀 |

## 4. 표준 표 5개

### 01_업체 (한 줄 = 협약사 한 곳)

| 열 | 뜻 |
|---|---|
| 업체명, 통합ID, 지역 | MOU 명부 기준 |
| 구분 | `YYYY 신규` / `2025 이전 기존` / `협약일 미확인` |
| 협약일 | MOU 체결일. 규칙으로 정정한 날짜는 확인 메모에 남김 |
| 최근 활동일 | 요청 활동 중 가장 최근 날짜 |
| L2 추세(9~10월), 기준선 L2, 비교 L2 | 플랫폼 기술자문 등록 일평균 비교(6/22~8/31 대비 9/1~10/31, ±25%, 기준선 3건 이상만 판정) |
| 올해·누적 L2 문의, L3 요청 | 요청 활동 건수 |
| 올해·작년 구매액, 마지막 구매일 | 판매 공급가액 합계(반품 차감, 운반비 행 제외) |
| KPI1 대상, KPI1 결과 | 대상·관찰 중·제외 / 활용(L2·L3)·구매로만 활용·미활용 |
| 확인 메모 | 협약일 미확인, 통합ID 없음, 기록 연결 안 됨, 협약일 정정 |

### 02_요청활동 (한 줄 = L2 문의 또는 L3 요청 하나)

| 열 | 뜻 |
|---|---|
| 활동ID, 날짜, 업체명, 통합ID | 활동ID = `원본시트:문의ID` 또는 `PT:번호` |
| 단계 | `L2 문의`(영업 진행 보고) / `L3 요청`(내역서 요청 또는 공법설명회 요청) |
| 단지, 공종 | 원문 그대로 |
| 출처 | 플랫폼 내보내기 / PT 일정 정리(잔디) |
| 상태, 종료 사유 | 플랫폼 상태 버튼 값. 진행중 / 완료(지원마감요청 = L4 도달) / 종료(영업 진행 철수 · 타공법으로 전략 수정 · 타공법으로 공고 업로드 · 동일공법 타사 낙찰 · 등록 실수). 업체가 안 누르면 진행중으로 남으므로 05_공고로 확인 |
| 단지키, 공종키, 사건유형, 사건일, 시간KPI유효, 제외사유 | **KPI 계산용. 열 이름을 바꾸지 말 것.** KPI 화면이 이 열을 읽음 |

- 같은 현장이라도 시공사가 다르면 따로 셈.
- "등록 실수"로 종료된 건은 요청에서 뺌. 견적서 초안 발송은 요청으로 셈.
- 12/24까지는 플랫폼과 앱이 동기화되므로 요청 ID로 중복을 뺌. 12/25부터는 앱 내보내기만 원천으로 씀.

### 03_판매 (한 줄 = 판매 전표의 품목 한 줄)

| 열 | 뜻 |
|---|---|
| 거래일, 업체명(명부), 통합ID, 거래처명(판매 기록), 전표번호, 품목, 수량, 공급가액(원) | |
| 명부 연결 | 연결됨 / 연결 안 됨(비협약 거래처이거나 표기가 다름) |
| 운반비 | 운반비 행 표시. 구매액 합계에서는 뺌 |

### 04_PT (한 줄 = 공법설명회 요청 하나)

| 열 | 뜻 |
|---|---|
| PT번호, 요청일, 예정일, 단지, 요청사(원문), 통합ID, 공법(원문), 담당 | |
| PT 상태 | 잔디 기록에서 읽은 상태: 요청 · 예정 · 일정 변경 · 취소 · 진행 여부 미확인 · 진행 완료 확인 |
| 실제 진행 | **담당자가 채울 칸.** 진행 완료 / 취소 / 일정 변경 / 미진행 |
| 감리 PT | 감리 PT 표시. 집계에서 뺌 |

- 분기 집계에서 감리 PT와 취소 PT는 L3로 세지 않음. "취소 후 재진행"은 셈.

### 05_공고 (한 줄 = 공고 하나)

| 열 | 뜻 |
|---|---|
| 공고번호, 공고일, 개찰일, 단지, 대표공종, 세부공종 | 공고문 대시보드 원본 기준 |
| 구분 | POUR / 타사 / 다특허 / 다특허(PD) 등 (원본의 구분 그대로) |
| 특허번호, 공법사, 공사명, 지역, 도시, 상태, 낙찰업체, 낙찰금액 | 낙찰은 L5 확인용 |
| 앞선 요청, 요청 업체 통합ID | 공고 전 365일 안에 같은 단지 요청이 있었는지. **이름 대조 추정값** |

- 플랫폼 상태(완료·종료)는 업체가 직접 누르는 버튼이라 빠질 수 있음.
- 그래서 L4 도달·실패는 이 표의 실제 공고 결과로 확인함. 같은 단지·같은 공종이 포어로, 타공법으로, 일반공고로 올라갔는지를 봄.
